Voice agent latency, explained

In a phone call, the only number that matters is how long the caller waits in silence after they stop talking before they hear a reply. This page shows where that time goes in a cascade pipeline, and why a fused speech-to-speech model is faster.

The cascade pipeline

Each turn passes through gates in series. The reply cannot begin until the first sentence is generated and synthesized, so every stage is felt as silence.

Telephony8 kHz mu-law media frames arrive over a WebSocket.
VADSilero waits for a silence tail to confirm the turn ended.
STTfaster-whisper transcribes the utterance (streamed to overlap speech).
LLMTokens stream, but TTS waits for the first full sentence.
TTSKokoro synthesizes the first sentence to audio.
PlaybackAudio is encoded to mu-law and paced back in 20 ms frames.

Why the LLM stage dominates

STT and TTS are small and stable. The LLM time-to-first-token is the largest and most variable stage, so it sets the floor. Streaming STT into the LLM (so it prefills while the caller is still talking) and starting TTS on the first short clause are the levers that matter most.

Serial gates stack

VAD, STT, LLM, and TTS run in order. Even small per-stage waits add up into one audible pause.

Tool turns cost double

When the model calls a tool it must generate the call, run it, then generate the spoken answer in a second pass. A short cached acknowledgement covers the gap.

Cascade vs fused, measured

Perceived latency here is measured from the call audio itself (caller stop to agent audio), using Silero VAD on each leg of the recording rather than the app's own trace.
