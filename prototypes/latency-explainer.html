Why the phone agent feels slow

Your architecture is cost-efficient and controllable, but each turn waits for several gates before the caller hears the first response frame. On RunPod, Kokoro appears to be running on GPU, so the main delay is the whole turn pipeline rather than TTS alone.

Current Design — three paths explored (2026-06-02)

Two brains were tried behind the same Telnyx telephony. OpenAI Realtime is the chosen production path (fastest); the self-hosted cascades are the alternatives if vendor lock / per-minute cost / voice-control ever outweigh raw latency.

OpenAI Realtime  CHOSEN

Fused STT+LLM+TTS in one hop, voice marin. first_audio ~333–365ms, full tool parity, clean barge-in, 0 errors on live calls. Tradeoff: vendor lock, OpenAI voice only, per-minute cost. Pod currently OFFLINE (killed at session end; one-command bring-up).

Local cascade — Claude brain

The self-hosted pipeline modeled below: whisper → Claude → Kokoro. TTFA ~1.05–1.3s (Claude TTFT ~600ms is the gap; micro-ack masks spikes). Fully ours, any voice. This is the Phase-5 baseline.

SLM cascade — Qwen default + Claude fallback  PARKED

Local Qwen3-4B-Instruct-2507 (bf16): TTFT ~376ms, tools 5/6. Chat-turn TTFA ~790ms, but tool turns ~1.3–1.6s+ and Claude-escalation turns are worse than Claude-alone. Self-hosted, any voice — parked: edge is thin exactly on the tool-heavy turns that matter.

This is the local cascade path (also what the model below tunes). Realtime collapses these gates into one hop. Inbound audio moves left to right; the outbound reply cannot begin until the first sentence is generated and synthesized.

GPU path

RunPod uses CUDA Torch and TTS_ENGINE=kokoro. When CUDA is visible, the code prints and uses Kokoro on cuda.

CPU path

If you run this shell locally, no GPU is visible. CPU Kokoro can still make TTS the dominant delay.

Serial pipeline

Pros and Cons of This Architecture

Pros

  • Low vendor lock-in and lower marginal cost.
  • Local STT, VAD, and TTS keep audio control in your process.
  • Barge-in is already supported with Telnyx clear.

Cons

  • Turn-taking is half-duplex, so every gate is felt as silence.
  • Claude punctuation timing controls when the first TTS job starts.
  • Local CPU runs behave very differently from the RunPod GPU image.

Best Fit

  • Works well for short, practical calls.
  • Needs careful response shaping to feel natural.
  • Needs timing logs per stage before changing providers.

Make the Conversation Feel Natural

1

Verify the runtime

Confirm the live pod logs show Kokoro on cuda and timing lines near the measured tts_first=69ms.

2

Shorten the first chunk

Prompt Claude to start with a short useful sentence and avoid repeating the cached acknowledgement.

3

Use audio fillers intentionally

Play cached phrases like "Got it" or "Let me check" immediately after STT, then synthesize the real answer behind it.

4

Reduce silence detection

The baseline was 600 ms. The code now defaults to 400 ms; confirm it does not clip slower speakers.

5

Move perceived audio earlier

Cache short acknowledgements and send them while the real answer is being produced. This improves feel even when total pipeline time is unchanged.
